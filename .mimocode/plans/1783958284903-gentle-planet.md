# Fix: All-in-One Container Startup Failures

## Context

The `logs.txt` captured from the all-in-one Docker container shows 23 of 27 microservices crash-looping on startup with two distinct errors, plus cosmetic issues. This plan addresses all 5 identified issues with minimal, targeted changes.

---

## Fix 1: Prisma `.prisma/client/default` MODULE_NOT_FOUND (23 services crash)

**Root cause:** `Dockerfile.all-in-one` line 397 runs `find services apps -name "schema.prisma"` to generate per-service Prisma clients in the runtime stage. This **excludes** `packages/shared-services/prisma/schema.prisma` because it's under `packages/`, not `services/` or `apps/`. Since shared-services has no custom `output` directive, it writes to the default pnpm-hoisted `.prisma/client/` location — but that location is never populated because the schema is skipped.

Every service that imports `PrismaService` from `@azeebo/shared-services` loads `@prisma/client` from the pnpm hoisted path, which has no generated client.

**File:** `Dockerfile.all-in-one` (line 397)

**Change:** Expand the `find` to also search `packages/`:
```
find services apps packages -name "schema.prisma" ...
```

This ensures the shared-services `AuditLog` client is generated and available at the pnpm hoisted `.prisma/client/` location that all services resolve to.

---

## Fix 2: `@azeebo/http-client` ERR_PACKAGE_PATH_NOT_EXPORTED

**Root cause:** `packages/http-client/package.json` exports field only defines `"import"` (ESM) but not `"require"` (CJS). All services use CommonJS (`require()`), so they fail to resolve the main export.

**File:** `packages/http-client/package.json` (lines 8-13)

**Change:** Add `"require"` condition:
```json
"exports": {
  ".": {
    "types": "./dist/index.d.ts",
    "import": "./dist/index.js",
    "require": "./dist/index.js"
  }
}
```

---

## Fix 3: Malformed ANSI escape codes in NestJS logs

**Root cause:** NestJS `ConsoleLogger` emits ANSI color codes to stdout. In the container (non-TTY, piped to supervisor), the ESC character is stripped but the sequence body remains as literal `;5;3m`.

**File:** `entrypoint.sh`

**Change:** Add `NO_COLOR=1` export near the top of the entrypoint (after line 16, before the first echo). This is the [no-color.org](https://no-color.org) standard — NestJS and many other tools respect it.

```bash
export NO_COLOR=1
```

---

## Fix 4: Prisma P3005 migration baseline error

**Root cause:** `entrypoint.sh` handles stuck migrations (P3009/P3018) but not P3005 ("database schema is not empty"). When a database has existing tables from a prior run but no `prisma_migrations` history, `prisma migrate deploy` fails with P3005. The current fallback only warns — it doesn't baseline the schema.

**File:** `entrypoint.sh` (lines 270-277)

**Change:** After each `prisma migrate deploy`, check the exit code and output for P3005. If found, baseline all pending migrations as "applied" using `prisma migrate resolve --applied`:

```bash
migrate_output=$(DATABASE_URL="..." prisma migrate deploy --schema="..." 2>&1) || {
  if echo "$migrate_output" | grep -q "P3005"; then
    echo "    Baseline existing schema for $svc_name (P3005)..."
    # Get all migration directories and mark them as applied
    for migration_dir in "$svc_dir/prisma/migrations"/*/; do
      migration_name=$(basename "$migration_dir")
      DATABASE_URL="..." prisma migrate resolve --applied "$migration_name" --schema="..." 2>&1 || true
    done
  else
    echo "    WARNING: Migration failed for $svc_name"
  fi
}
```
