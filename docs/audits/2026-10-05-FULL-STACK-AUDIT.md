## 1. Executive Summary

Architecturally, Azeebo+ is a mature, heavily instrumented enterprise monorepo: 29 NestJS microservices behind a single gateway with deny-by-default GET caching, strip-and-reinject identity headers, timing-safe gateway secrets, and fail-closed Redis throttling; 5 client apps sharing React Query v5 and one of the strictest TypeScript/ESLint baselines this auditor has seen (~300K lines of TS, only 19 `: any`, zero-warning lint ratchet at 56 workspaces); 70% coverage floors enforced in 28/29 services; a shadow-DB migration drift gate; and a CI estate with gitleaks, Trivy, CodeQL, supply-chain provenance attestation, and an `audit-gate` blocking on high/critical vulnerabilities. The prior audit's P0 remediations are genuinely landed and verifiable in code.

The highest-risk findings now concentrate in three places. **First, money-path integrity:** wallet withdraw and transfer synthesize idempotency keys server-side from `Date.now()`, so a client retry after timeout produces a fresh key and a duplicate debit — a double-spend window on the platform's core financial primitive (`services/core/wallet-service/src/modules/wallet/wallet.service.ts:566,670`), compounded by a fully-built `IdempotencyGuard` that is wired nowhere and an `Idempotency-Key` header the gateway strips from its own allowlist. **Second, destructive self-healing in deploy/entrypoint.sh:** the P3018 recovery path can run `DROP SCHEMA public CASCADE` in a production-classified all-in-one deploy, and the P3005 path marks every migration `--applied` without executing its SQL, while the stuck-migration pre-pass queries a misspelled `_prisma_migrations` table (missing underscore) so it silently never works. **Third, privacy/compliance:** analytics `POST /events` ingests client-supplied payloads (including web-vitals metadata passed through verbatim) with no authentication and no server-side consent enforcement against a 3-year PII store, DSAR erasure leaves `phone`, `payment_methods`, messages, and S3 objects behind, and the retention enforcement script is dry-run-by-default, scheduled only via a macOS LaunchAgent, and hardcodes dev DB credentials.

The strongest patterns worth preserving: the gateway trust boundary (client `x-user-*` stripped before routing, re-injected only from a verified JWT, downstream services failing closed on missing/timing-safe-verified `x-gateway-secret`); raw-body HMAC + replay-window + idempotency webhook security; `SELECT … FOR UPDATE` pessimistic locking in every wallet mutation inside interactive transactions; parameterized-only raw SQL (including `Prisma.join` batching); per-workspace lint-warning ratchets that can only move down; and a Lighthouse CI budget that fails the build on performance regressions. With the P0/P1 remediations below, this platform is on a credible path to Production Ready.

## 6. Follow-up pass (2026-10-07) — AUD-77 and AUD-78

Both surfaced while running the platform end-to-end on the local dev stack (gateway `:3013`, web `:4000`, admin `:4100/4016`, creator `:4101/4014`) and stopping a service to observe real outage behaviour, rather than by reading code.

### 6.1 AUD-77 — the silent-failure class (High)

**Root cause (one defect, replicated in three clients).** None of the app fetch layers reject on a failed read. `apiFetch` resolves non-2xx and network failures as an envelope — `apps/web/src/lib/api/base.ts:610,642,661,675,702,724` all `return { success: false, … }`. Every `queryFn` then did the "defensive" thing:

```ts
// Before — the outage is laundered into a successful empty result
queryFn: async () => {
  const res = await apiFetch<T[]>('/v1/commerce/counterparty');
  return res.success ? res.data : []; // ← react-query sees status:'success'
};
```

Consequences were worse than an ugly error state:

- `isError`, `error`, and every hand-written error branch in these components were **unreachable code** — a reviewer reading the file would believe the page handled failures.
- Headline figures were _computed_ from the fallback, so a 503 rendered as an assertion about the business: `Total Exposure ₦0`, `0 refunds`, `0 rows`, `0m streamed`, and on detail routes a full **404-shaped** "Venue Not Found" / "Film not found" page for a service that was merely restarting.
- No retry affordance, since the component thought it had succeeded.

**Fix contract (applied uniformly, three clients).**

1. **Throw in `queryFn`** through shared guards so react-query actually transitions to `status:'error'`: `requireData`/`requireArray`/`messageOf` in `apps/web/src/lib/payload.ts`, `assertSuccess`/`requireData`/`asArray`/`unwrapList` in `apps/admin/client/src/lib/payload.ts:33-104`, `assertSuccess`/`errorMessage` in `apps/creator/client/src/lib/api/creator.ts:40`.
2. **Make the error surface reachable** — `ErrorState` (`packages/ui/src/web-components.tsx:617`) with the server's own message and a working `Retry` → `refetch()`.
3. **Withhold quantitative claims instead of computing them.** A failed dashboard read renders `—` in every stat, never `0`/`₦0`.
4. **Outage ≠ not-found.** Detail routes got a third branch: `isError` → "unavailable + Retry", `!data` → the genuine not-found page. Previously both collapsed into not-found.

**Surface area closed:** 13 web route files (commerce counterparty / revenue-classes / telco-reconciliation / refund-status, creator analytics-dashboard, lifestyle places + tonight + influencers, live event, cinemaxis film + ticket, admin process-mining + capacity-ledger, movies watchlist), 30 admin SPA files, 19 creator SPA files. ### 7.1 AUD-79 — the panels collected credentials they never needed (Medium)

**Request.** Both the admin Console and the Creator Studio must sign in through the main web app.

**What was actually wrong.** No new session mechanism was needed — the platform already has one. The web app mints `access_token` (15 min) and `refresh_token` (24 h) as httpOnly cookies (`apps/web/src/app/api/auth/set-cookie/route.ts`); the gateway falls back to `request.cookies.access_token` (`gateway-auth.guard.ts:168`) and `/auth/cookie` is public (`gateway-auth.guard.ts:40-44`); cookies are host-scoped, not port-scoped, so one browser jar on `localhost` covers web `:4000`, admin `:5173/4016` and creator `:5174/4014`, and in production the gateway serves `/admin` and `/creator` on the same registrable domain. The defects were at the edges:

- **Creator had no cookie session at all.** `apps/creator/client/src/context/AuthContext.tsx` restored a session by reading a **localStorage user blob plus a readable token**, so a reload of a cookie-authenticated creator logged out — the same class of bug as AUD-77's silent failures, in the auth path.
- **Both panels kept a password form** (`routes/login.tsx`) that posted `/auth/login`, then mirrored tokens into `setAuthCookies`/localStorage. Two credential surfaces for one platform, and the only way to reach the panel was to re-enter the password.
- **The web login's own redirect guard was open at the edges.** The previous inline check accepted same-origin paths but had no notion of a _cross-origin_ first-party target, which the hand-off now requires.

**Fix.**

1. `apps/web/src/lib/first-party-redirect.ts` (new) — `safeRedirectTarget(raw, fallback, allowedOrigins)` keeps same-origin paths, and accepts an absolute URL only when it is http(s), has no userinfo, and its `URL.origin` is an **exact** member of `NEXT_PUBLIC_PANEL_ORIGINS` (comma-separated, trailing slashes normalised). Everything else collapses to the fallback. `isSafeSameOriginPath` rejects `//host` and `\host` because browsers normalise the latter to the former, and rejects `://` so `javascript:` and scheme tricks cannot pass. Matching on `URL.origin` rather than a string prefix is what stops `https://admin.azeebo.com.evil.com`, `https://evil.com/?next=https://admin.azeebo.com/` and `http://admin.azeebo.com@evil.com/`.
2. `apps/web/src/app/auth/login/page.tsx` — resolves `?redirect=` through that helper; absolute targets navigate with `window.location.assign` because `router.push` cannot leave the origin, same-origin targets keep `router.push`.
3. `apps/{admin,creator}/client/src/lib/web-auth.ts` (new, near-identical) — `webLoginUrl(next)` builds `${WEB_APP_URL}/auth/login?redirect=<absolute same-app URL>` where the return path is filtered by `safePath` (rejects `//` and backslash), and `goToWebLogin` uses `location.replace` so the hand-off page is never a back-history entry. `VITE_WEB_APP_URL` overrides the `http://localhost:4000` default. Creator's copy adds `webRoleSelectionUrl()` for the "not a creator yet" path.
4. Both `AuthContext.tsx` — the credential `login()` is gone; the provider now **probes** `GET /api/v1/auth/me?_t=…` through `apiFetch` (which carries the cookies and rotates an expired access token first, so a _readable_ token is deliberately not part of the test) and sets `roleDenied` when the session is live but the role is not this panel's. `logout()` clears the shared session and hands back to the web login. Creator's `ALLOWED_ROLES` stays exactly `{'creator'}`; admin's keeps its six admin/superadmin spellings.
5. Both `routes/login.tsx` — the forms are replaced by a branded hand-off card that auto-hands-off and still offers a click-through anchor (needed, because `location.replace` is blocked in some embeds). **Loop guard:** an unauthenticated visitor is handed to the web app, but a `roleDenied` visitor is not — sending a signed-in non-admin to the web login returns them here with the same session, forever. The denied branch offers "Sign in with an admin account" / "Apply for creator access" / "Back to Azeebo+".

### 8.1 What is actually broken

Four independent gaps, in the order a user would hit them:

1. **The buttons issue a GET against POST-only routes.** `apps/web/src/app/auth/login/page.tsx:173,202` set `window.location.href = /api/v1/auth/social/{google,apple}`. `next.config.js:120-129` rewrites `/api/*` to the gateway; the proxy registry declares those paths `POST` only (`proxy.controller.ts:101,107`). Observed: `GET http://localhost:3013/api/v1/auth/social/google` → `404` with a problem-details body, so the user is left staring at raw JSON.
2. **The real entry point is not callable while signed out.** `GET /social/{p}/authorize` → `401 Authentication required`. The controller declares only `FeatureFlagGuard` + `RateLimitGuard` (`social.controller.ts:55-64`), so the requirement is the gateway's `gateway-auth.guard.ts` public-path list, not the service. A login page's first action must not need a session.
3. **Authorize returns JSON, not a redirect.** The handler resolves `{ state, authorizeUrl }` (`social.controller.ts:65-70`), so navigating a browser at it shows JSON instead of sending the user to the provider. Nothing in any client consumes it.
4. **There is nowhere for the provider to come back to.** `buildAuthorizeUrl` sets `redirect_uri` to `${BASE_URL}/auth/social/callback?provider=…` where `BASE_URL` is the **auth-service's own** origin (`social.service.ts:274-275`), and that route is `@Post('callback')` (`social.controller.ts:93`). Google would GET it; Apple form-POSTs it. Neither lands in the web app, and `apps/web/src/app/auth/` has no callback route (only `expired-session, forgot-password, login, otp-verification, profile-setup, register, reset-password, role-selection`). So even with credentials, code exchange would never be triggered from a browser.

Also worth noting for whoever picks this up: `NEXT_PUBLIC_AUTH_URL` is referenced **only** by these two lines and is defined in no env file, so it always evaluates to `''` — the URLs are same-origin-by-accident, which is why the Next rewrite masks the misconfiguration.

### 8.2 Scope of the feature

- **Gateway:** add `/auth/social/{google,apple}/authorize` to the public-path list; keep `POST /auth/social/callback` authenticated-public (it carries no session by definition). Update the `endpoints` table to match whatever is finally exposed — that table is the ratchet other findings already treat as authoritative.
- **auth-service:** make the authorize entry a `302` to the provider URL (or keep the JSON endpoint for non-browser clients and add a redirecting one). Move the browser callback off the service origin onto the web app, keeping `GOOGLE_REDIRECT_URI` / `APPLE_REDIRECT_URI` as the single source of truth rather than a `BASE_URL`-derived default.
- **Return target (the AUD-79 hand-off):** carry the panel `redirect` **inside the server-side `state` record** (`STATE_PREFIX` + Redis, `social.service.ts:150-185`), not as a provider-visible query param. On callback, resolve it through `safeRedirectTarget` + the `NEXT_PUBLIC_PANEL_ORIGINS` allowlist already built in §7.1, so both paths share one defence.
- **apps/web:** new `auth/callback/page.tsx` — read `code`/`state`, `POST /auth/social/callback`, then `POST /auth/cookie` so the shared httpOnly jar is set exactly as the password path does, then `window.location.assign` for an allowlisted absolute target or `router.push` otherwise. Needs a GET handler for Google and a form-POST handler for Apple, plus an explicit error branch: today every failure mode renders as JSON.
- **Buttons:** point at the authorize entry, and give them a loading/disabled state so a provider outage is visible instead of a navigation into a 404.

### 8.3 Hard blockers before any of this can be verified

- `GOOGLE_CLIENT_ID` / `GOOGLE_CLIENT_SECRET` and `APPLE_CLIENT_ID` / `APPLE_CLIENT_SECRET` are not configured in any local env file, and `buildAuthorizeUrl` will happily mint a URL with an empty `client_id` — a silent misconfiguration worth asserting on.
- Redirect URIs must be registered in the Google Cloud console and (for Apple) a Services ID + key pair; Apple additionally requires a real domain, so a localhost-only loop is not achievable for that provider.
- Consequence: the code can be written and unit-tested, but **the end-to-end flow cannot be proven from this machine**. Verification therefore has to be in-project tests for every branch that does not require a live provider (state round trip, allowlist enforcement, cookie hand-off, error rendering), and one manual pass in a staging environment with credentials for the legs that do.

### 8.4 Acceptance criteria

1. Signed-out browser can reach the authorize entry and is taken to the provider (no 401, no JSON page).
2. Returning with a valid `code` establishes the same httpOnly session the password login establishes, and `GET /api/v1/auth/me` with **cookies only** authenticates.
3. `?redirect=` to an allowlisted panel origin returns the user to the panel; `//evil.example`, a non-listed first-party origin, and a bare path all resolve to the documented fallbacks — the same table §7.1 pins in `first-party-redirect.test.ts`.
4. Tampered/expired `state` is rejected without revealing which, matching the existing anti-enumeration posture.
5. Provider error (`?error=access_denied`, callback failure) renders the login page with a message; no raw JSON reaches a user.
6. `auth_social_google` / `auth_social_apple` kill switches still turn each provider off end-to-end.
7. Web + admin + creator suites, both `typecheck:client`s and `check-dead-exports` stay green.

### 8.5 Interim state, and the decision this schedule leaves open

**Closed 2026-10-08 — see §9.1.** Until this is built, the two buttons on the platform's login page took web, admin and creator users to a 404. The honest interim options were (a) hide/disable them with a "coming soon" affordance, or (b) leave them visible and accept the broken path. (a) is now implemented: the buttons render disabled, non-navigating, with an explicit caption, and the dead `NEXT_PUBLIC_AUTH_URL` references are gone. ### 9.9 AUD-90 (new, Medium, fixed) — `check:env` was blind to the reads that matter most

`scripts/check-env-consistency.mjs` reported `.env.example` entries as `STALE-EXAMPLE` ("documented but nothing in this service reads it") for keys the service reads on every boot. The cause was one character: `GET_RE` ended `\s*(?:,)`, so a **trailing comma was mandatory** and only `config.get('KEY', fallback)` counted. The no-default form — `config.get('KEY')`, which is what a _required_ key looks like — never matched, so its documentation appeared stale. The file's own header already promised the opposite ("MISSING-SOFT — code reads via configService.get('KEY') without a code-level default"), so this restores stated intent rather than inventing policy.

**Fix:** `\s*[,)]` — the value may end at a comma or at the closing paren. `.getOrThrow` cannot be swallowed (its `(` is not immediately after `get`), and the `[A-Z][A-Z0-9_]{2,}` key shape keeps `map.get('camelCase')` out. No receiver anchor is imposed on purpose: config arrives as `configService`, `config`, `cfg` and destructured helpers across 29 services, so anchoring would trade one blind spot for another.

**Measured, before → after:** `STALE-EXAMPLE` **130 → 111**, `MISSING-SOFT` 120 → 146, `MISSING-REQUIRED` 0 → 0, exit `0` either way. All 19 cleared stales were checked by hand and each is a real no-default read in that service — `APPLE_PRIVATE_KEY`/`APPLE_TEAM_ID`/`APPLE_KEY_ID`/`APPLE_REDIRECT_URI`, `GOOGLE_CLIENT_SECRET`/`GOOGLE_REDIRECT_URI` (auth), `FIREBASE_PROJECT_ID`/`FIREBASE_CLIENT_EMAIL`/`FIREBASE_PRIVATE_KEY` (notifications), `FLUTTERWAVE_SECRET_KEY` (payments), `CONTENT_DATABASE_URL` + four `SEARCH_INDEX_*` (search), `S3_ENDPOINT` + `MEDIA_CDN_FLAG_POLL_MS` (media), `MEDIA_SERVICE_URL`, `WALLET_SERVICE_URL`. **Zero stale findings were added**, so nothing was masked. The 26 new `MISSING-SOFT` warnings are keys that were previously invisible and are undocumented — honest new signal, non-blocking, and deliberately not swept into this change.

**Testable now.** The script ran its whole check at import, so it could not be tested. Its entry point moved behind `if (import.meta.url === pathToFileURL(process.argv[1]).href) main()` — the same guard `scripts/audit-gate.mjs:177` uses — and the scanner regexes plus `findEnvReads` are exported. `scripts/__tests__/env-consistency-reads.test.mjs` pins four cases against a temp fixture: both `get()` shapes (with and without a default, plain and generic-typed), `getOrThrow` staying strictly strict, non-env-shaped literals and variable reads ignored, and `NODE_ENV`/`PORT` still filtered. **Proven non-vacuous:** swapping the old `\s*(?:,)` back in fails case 1 and nothing else.

**Verified:** `node --test scripts/__tests__/env-consistency-reads.test.mjs` 4/4; `pnpm run check:env` exit 0; script still Prettier-clean.

### 9.10 AUD-91 (new, High, fixed) — Apple ID tokens were accepted for the wrong client

`SocialAuthService.verifyAppleToken` — the only verifier on the live `POST /auth/social/callback` path — checked the RS256 signature against Apple's JWKS and required an `email`, and stopped there. **`iss` and `aud` were never compared to anything.** Apple signs ID tokens for every client with the same JWKS, so a valid signature proves only _"Apple issued this"_, not _"Apple issued this to us"_: a token minted for any other developer's Services ID verified here, and `socialLogin` then signed its holder into whatever account its `email` claim named. That is the same account-takeover endpoint as AUD-85, reached with a genuinely Apple-signed token instead of a forged one.

**Fix, in `modules/auth/social/social.service.ts`:** after `jwt.verify`, `iss` must equal `https://appleid.apple.com`, and `aud` must contain this deployment's Services ID (handled as `string | string[]`, since the JWT spec allows either). The expected value comes from a new `AppleClientSecretService.getClientId()` rather than a second config read — it is the same Services ID that already appears as the `sub` of the minted client secret, so there is one source of truth, and it **throws 503 when unset**, which makes the audience check fail closed instead of being skipped on an unconfigured deployment.

**A second defect surfaced while testing the first.** A token signed by anything else came back as **500**: the catch block funnelled every non-`UnauthorizedException` into `mapAndThrow`, which maps an unknown error to `InternalServerErrorException`. A forged, expired, or malformed token is the caller's fault, so every hostile request looked like a server fault and would have paged an on-call. JWT verification failures (`JsonWebTokenError`/`TokenExpiredError`/`NotBeforeError`) now map to `401 Apple token could not be verified`, with the `allowed-fabricated-4xx` annotation this repo requires when a 4xx is thrown inside a catch block.

**Not changed:** `modules/social-auth/social-auth.service.ts` (AUD-85) still verifies nothing at all, so adding claim checks there would be decoration — an attacker simply sets `iss` and `aud` correctly. That endpoint needs signature verification or removal, which is still the open decision.

**Verified.** `social.apple-claims.spec.ts` signs real RS256 tokens with a generated key and serves its public half as Apple's JWKS, so the signature path executes rather than being stubbed: it pins acceptance for the correct client, acceptance of an audience _array_ containing it, and rejection for a foreign client, a foreign issuer, a missing issuer, a missing audience, an audience array without our id, and a foreign signing key — plus a 503 when the client id is unconfigured. **Non-vacuous:** deleting the two claim checks fails exactly the five claim-rejection cases and nothing else. `auth` + `social-auth` + `device-link`: **16/16 suites, 181/181 tests**; `tsc --noEmit` exit 0; ESLint and Prettier clean.

### 10.3 Where Expo's matrix was not followed, and why

- **`@react-native-async-storage/async-storage` kept at 3.1.1 in both apps** although the SDK 57 map asks for 2.2.0. `packages/react-data` — the shared package both apps consume from source — declares async-storage **3.1.1 as a direct dependency**, so honouring the map put two copies of a native TurboModule in one app graph. - **`react-native-safe-area-context` accepted the map's downgrade** 5.8.0 → 5.7.0 in both apps: only the apps declare it, no shared package does, so no duplicate arises.

- **`@expo/dom-webview@~57.0.1` declared in both apps.** `expo` 57 has it as an optional peer; while the two apps sat on different SDKs, pnpm satisfied mobile's peer from `apps/tv`'s SDK 56 copy, and doctor's "overridden dependencies" check failed with _"expo should install @expo/dom-webview@~57.0.1, but 56.0.6 is installed"_. On TV it also earns its keep: setting the block **before** running `--fix` is what stops that command from silently re-downgrading async-storage and re-breaking `packages/react-data`.
- **`app.json` plugins gained `expo-status-bar` and `expo-video`** in both apps. SDK 57 turns both into config-plugin-aware modules; the CLI reports this and, because both projects use a dynamic `app.config.js`, prints the change instead of writing it. `app.config.js` spreads `base.expo`, so adding them to the static `app.json` array is the right home.

### 10.6 AUD-84 (High) — the image-size security override broke SDK 56's bundler — **RESOLVED by the TV upgrade**

Established while trying to tell whether this upgrade had broken `apps/tv`: `pnpm --filter @azeebo/tv run bundle:check` (a PR-gate job) fails after ~1517 modules with

```
SyntaxError: …/expo-router@56.2.16/…/assets/pkg.png: The "list" argument must be an
instance of SharedArrayBuffer, ArrayBuffer or ArrayBufferView.
```

It is not a stale cache — re-running with `--clear` fails identically, on a _different_ PNG each time (`unmatched.png`, then `pkg.png`), which is what a broken code path looks like rather than a broken file.

**Cause.** The workspace's security override `image-size: ">=2.0.3 <3"` (root `package.json`) rewrites every `image-size` in the graph to 2.0.4. `metro@0.84.4` — the bundler that Expo SDK 56's `@expo/metro-config` uses, and which declares `image-size: ^1.0.2` itself — calls the **default export** as a function (`metro/src/Assets.js:17` `_interopRequireDefault(require("image-size"))`, used at `:72` and `:177`). image-size 2.x does not export a callable default of that shape, so metro hands it something it cannot wrap in a `Buffer` and the PNG dimension probe throws. Any app on the old bundler therefore cannot bundle an asset catalogue at all.

**Why this upgrade did not cause it, and is in fact the remedy.** `image-size@2.0.4` was already resolved at `HEAD` (the override predates this pass), and the SDK 57 bump does not touch tv's tree. Mobile exports cleanly because RN 0.86 / Expo 57 pull `metro@0.84.5`, which declares **no** `image-size` dependency and uses a different asset path. So the conflict is specific to SDK 56's bundler.

**Two ways out were on the table, and the user picked the first:**

1. Upgrade `apps/tv` to SDK 57 as well (the same procedure as §10) — removes the incompatible bundler rather than weakening the override. **Chosen.**
2. Scope the override so metro's copy stays on the 1.x line it was written against (e.g. a pnpm scoped override `"metro@0.84.4": {"image-size": "1.2.1"}`). It un-ships the vulnerable version from the _build_ toolchain only — image-size is not in any runtime bundle — but it deliberately re-admits the advisory the override was added to close, so it would have needed an explicit sign-off. It is no longer needed.

**Resolution evidence (§10.7):** `pnpm --filter @azeebo/tv run bundle:check` now exits 0. `metro@0.84.4` is gone from `pnpm-lock.yaml` — the graph carries only `metro@0.84.5` and `0.84.6`, and both were confirmed to declare no `image-size` dependency and contain no `image-size` reference in `src/Assets.js`. `image-size@2.0.4` remains in the tree for its other consumers, still under the security floor, and nothing in the Expo bundler path touches it any more. The override was not weakened at any point.

## 11. Follow-up pass (2026-10-15) — a PR gate that had gone blind, and what its noise hid (AUD-87)

Found while looking for regressions from the SDK 57 dependency churn, not while working on it: `pnpm run check:build-chain` fails on a tree where **none** of its inputs is modified, so it has been failing at `HEAD` for four days — and `.github/workflows/pr-checks.yml:109` runs it on every PR.

Two separate defects were tangled together, and they needed opposite remedies:

**1. The checker had gone blind to a spelling it should accept.** Its rule is that a per-service image must build through the _workspace build script_ (the shared runner pinned by `check:dev-wiring`), routed either as `pnpm --filter @azeebo/<svc> run build` from `/app` or as `WORKDIR …/<svc>` + bare `pnpm run build`. Commit `033f4398` (2026-10-11) moved 28 of the 29 service Dockerfiles to `pnpm --filter ./services/<group>/<svc> run build` — a valid pnpm filter that does route through the same script — but `SERVICE_FILTER_BUILD_RE` (`scripts/lib/build-chain-core.mjs:246`) matched only `@azeebo/…`, so every one of those images was reported as `NO_BUILD_STEP`, with a `fix:` telling an engineer to rewrite a Dockerfile that was already correct. One Dockerfile still used the name form, which is why the count is 28 and not 29.

Fixed in the checker, not in the tree: the regex now accepts a package name **or** a path target, and routing is decided by comparing that target against the service's own workspace-relative directory (`build-chain-core.mjs:302-310`). A path filter aimed at a different workspace is still not routed — that case is a test, as is the passing one. Rewriting 28 Dockerfiles to satisfy a stale regex would have been churn with a real cost: the path form is what the tree converged on, and the gate is supposed to follow the contract, not manufacture one.

**2. One finding in the same output was genuine.** `@azeebo/logger` was chained at position 6 while `@azeebo/security` sat at position 12, and `packages/logger/package.json` declares `@azeebo/security: workspace:*` with both `main` and `types` pointing into `dist/`. Nothing breaks on a dev host because stale `dist/` directories persist; in the image, `.dockerignore` excludes `dist/`, so `logger`'s `tsc` compiles against a `@azeebo/security` that has not been built yet. This is precisely the class the gate exists to catch — its header records the earlier feature-flags/shared-services version of the same bug, and notes each occurrence cost a ~15-minute build cycle to discover. `@azeebo/security` moved to just before `@azeebo/logger`; its only internal dependency is `@azeebo/shared-types` (position 1), so the new slot is topographically safe, and the duplicate step that the move left further down was deleted.

Verification:

- `node --test scripts/__tests__/build-chain.test.mjs` → **21 pass / 0 fail** (19 existing + the 2 new routing cases).
- `node --test scripts/__tests__/*.test.mjs` (the PR-gate step at `pr-checks.yml:125`) → **782 tests, 774 pass, 0 fail**.
- `pnpm run check:build-chain` → exit 0: _"Docker build chain OK (51 chained builds, topologically consistent across 57 workspaces). Per-service Dockerfiles OK (29/29 services route through the workspace build script)."_
- Unrelated gates checked in the same sweep because the SDK pass touched shared packages: `check:expo-routes` ✅ (261 files, 213 navigation targets, 170 routes) and `check:dead-exports` ✅ (ratchet holds; the new `DeepLinkRouter` export did not raise the floor).

**Why it stayed red for four days, and what to carry:** a gate that fails for a _spelling_ reason trains everyone to read its output as noise, and the one signal inside that noise — a real order violation that only manifests in CI images — was invisible. Two habits follow: when a gate goes red and none of its inputs changed, check which side drifted (here: `git log` on the checker vs the Dockerfiles, and count how many files use each form before deciding which is authoritative); and prefer encoding a gate's rule in a test over a regex-only match, which is what let the path form through unnoticed.

### 12.1 What the gate actually enforces, and why a missing doc line is a runtime bug

`scripts/check-route-contracts.mjs` has two passes, and only reading its headline makes either one look cosmetic:

- **Client → gateway.** Every `/api/v1/<service>/…` literal in `apps/web`, `apps/mobile`, `apps/admin/client`, `apps/creator/client` must match a `SERVICE_CONFIGS` endpoint on _service + path + method_. A path that matches with the wrong verb is reported separately as a mismatch, because that is the difference between a working call and a 405.
- **Gateway → backend.** Every declared endpoint must exist in the upstream Nest controller (`scripts/lib/gateway-backend-contracts.mjs`), and every backend route should be declared.

The declarations are not decoration. `ProxyController.isDeclaredEndpoint()` (`proxy.controller.ts:3905`) treats the same `endpoints` array as a **deny-by-default allowlist** whenever the `gateway_endpoint_enforcement` flag is on: anything not in the manifest gets `404 Endpoint not found` at the gateway and never reaches the service (`proxy.controller.ts:4076-4080`). So a call implemented upstream and missing from the manifest is a time bomb armed by a flag flip, not a documentation nit.

### 12.3 AUD-89 — the env gate is right about the gap and wrong about the crash, and its fix is a file class off-limits

`node scripts/check-env-consistency.mjs` exits 1 with 28 blocking findings across 28 services. They are one finding repeated: `✗ MISSING-REQUIRED: DIRECT_DATABASE_URL — getOrThrow at prisma/schema.prisma:10 — boot crashes without it, but .env.example omits it`.

Established, not assumed:

- **The variable is real and required by the schema.** All 27 service schemas plus `packages/security/prisma/schema.prisma` declare `directUrl = env("DIRECT_DATABASE_URL")` beside `url = env("DATABASE_URL")`.
- **Prisma does reject its absence.** With the auth schema copied to `/tmp` (no `.env` in scope, so the service's own file could not mask the result), `DATABASE_URL` set and `DIRECT_DATABASE_URL` unset, `prisma validate` fails with a `getConfig` validation error pointing at the `directUrl` line. The checker's "prisma schema env() counts as a strict read" rule (`check-env-consistency.mjs:158`) is therefore not a false positive.
- **It is not a boot failure.** `directUrl` is a migration-time property consumed by the Prisma CLI; the generated client connects with `url`. The message the gate prints — "boot crashes without it" — overstates the consequence, even though it flags a genuine hole.
- **Nothing is broken today.** `deploy/entrypoint.sh:299,311,325,355` passes both variables explicitly into every `prisma migrate` / `db push`; `scripts/database/apply-pgbouncer.mjs:145` writes `DIRECT_DATABASE_URL=<original URL>` into each service's `.env` when it moves `DATABASE_URL` behind PgBouncer — which is where the `directUrl` lines came from — and both keys are present in the gitignored local `.env` files. The gate's own design (`RUNBOOK.md:714`) documents that split. The only false thing is the claim that an engineer following `.env.example` gets a booting service: they get a service that boots and an image whose entrypoint migration step fails.

So the finding is a **documentation-completeness gap in 28 tracked templates**, and the tool's sole remedy is "add the keys to the service's `.env.example`". That is precisely the file class that has been reverted here three times when I have touched it, and a 28-file sweep is exactly the kind of scope decision that should not be made unilaterally. It is left red and reported, with three mutually exclusive options:

1. **Document it** — one line per `.env.example`, commented as migration-only, e.g. `DIRECT_DATABASE_URL=postgresql://…` alongside `DATABASE_URL`. Gate goes green, template stays truthful about what Prisma needs. Needs 28 tracked-file edits.
2. **Fix the checker's severity, not the tree** — treat a `directUrl = env(…)` reference as advisory (it is not read by the runtime client) and keep `url = env(…)` blocking; the wording should say "Prisma CLI/migrations fail without it", not "boot crashes". Gate goes green with one file changed, at the cost of no longer catching a genuine pooler-config typo in `directUrl`.
3. **Leave it red** as a standing reminder until the templates are revised on purpose.

No code, schema, or client change is required for any of the three, and none was made.

## 13. Follow-up pass (2026-11-06) — one route table for social sign-in (AUD-85 closed)

**The defect was a routing accident with a security consequence.** Two controllers declared `@Controller('auth/social')` in the same service: `modules/auth/social/social.controller.ts` (registered by `AuthModule`) and `modules/social-auth/social-auth.controller.ts` (registered by its own `SocialAuthModule`, imported by `AppModule`). Both were live, both had their own `SocialAuthService`, and Nest resolves overlapping routes by module registration order. The second table's `google/authorize`, `apple/authorize` and `unlink` therefore never ran — dead routes that built provider URLs from raw env vars and returned `{url}` — while its `login` and `accounts` did. So the service had one verified Apple implementation (JWKS + `iss`/`aud`) and one that decoded the token payload and trusted it, reachable at `POST /auth/social/login` for anyone who could base64 a JSON body (AUD-85).

**Consolidated.** One controller (`modules/auth/social/social.controller.ts`) now owns every `/auth/social` route, backed by the one verified `SocialAuthService`; `modules/social-auth/**` and the unused `auth/social/social.module.ts` are deleted, and `AppModule` no longer imports a second social module. The two routes that only the duplicate owned were moved rather than dropped:

- `GET /auth/social/accounts` — reads `AuthRepository.listSocialAccounts(userId)`; authentication comes from the global `ServiceAuthGuard` exactly as before.
- `POST /auth/social/login` — kept because the gateway advertises it to older native clients, but it no longer has its own verifier. `SocialAuthService.loginWithCredential` routes Google to `tokeninfo` and Apple to the JWKS verifier (signature, `iss`, `aud`), then through the same account-linking flow as the browser callback. That closes AUD-85: a hand-built token now fails at signature verification and no user lookup happens. `SocialLoginDto` moved to `modules/auth/dto/social-login.dto.ts` with its per-provider `@ValidateIf` rules intact, and its response keeps the legacy camelCase shape (`{ accessToken, refreshToken, user }`) so older callers do not break.

**Two related fixes found while merging the annotation sets:**

- The surviving table had no `@Public()` anywhere, so the global `ServiceAuthGuard` answered `401` on `/auth/social/google/authorize`, `/apple/authorize` and `/callback` before the provider redirect was built — precisely the signed-out flow §9.10's PRD requires to work. The duplicate table had marked its own copies public; those annotations now live on the single table (`login`, `google`, `apple`, `callback`, both `authorize` routes). `accounts` and `unlink` stay authenticated.
- `verifyAppleToken` read the JWT header with a bare `JSON.parse`, so any caller-supplied `a.b.c` string produced a 500 from the (public) verifier. It now fails closed with `401 Invalid Apple token format`.

**Provider kill-switches.** The combined legacy route carries the provider in the body, so a single `@FeatureFlag` cannot gate it: the handler checks `authFlags.socialGoogle` / `socialApple` for the provider actually named and returns 403 otherwise, matching `FeatureFlagGuard`. Turning Google off no longer blocks Apple sign-in and vice versa.
